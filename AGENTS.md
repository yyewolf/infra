# Home network infrastructure

Terraform-managed home network config using the MikroTik RouterOS provider and SOPS for secrets.

## Structure

```
.
├── router/           # MikroTik router configuration
│   ├── main.tf       # Root: providers, data sources, module calls
│   ├── provider.tf    # RouterOS provider (192.168.1.49, insecure=true)
│   ├── variables.tf   # wan_interface, wan_hostname, lan_interface_list, wan_interface_list
│   ├── router-sops.yaml   # SOPS-encrypted router credentials (secrets.username, secrets.password)
│   └── modules/
│       ├── wan/          # DHCP client, ethernet, DNS, mDNS
│       ├── ip-firewall/  # IPv4 firewall filter + NAT rules
│       ├── ipv6-firewall/# IPv6 firewall filter + address lists
│       └── wireguard/    # WireGuard interface, IP, and peers
├── wireguard/
│   ├── identities-sops.yaml  # SOPS-encrypted WG identity registry
│   ├── gen-identity.sh       # Generate keypair for one identity
│   ├── gen-conf.sh           # Render a client .conf for one identity
│   └── gen-all.sh            # Regenerate all keys
├── openstack/            # Infomaniak OpenStack: the edge-0 Talos worker
│   ├── main.tf           # Glance image, port + secgroup, instance, floating IP
│   ├── provider.tf       # OpenStack + SOPS providers
│   ├── variables.tf      # flavor, networks, instance name
│   └── tf.sh             # State encryption wrapper
├── talos/                # Talos cluster definition (see talos/README.md)
│   ├── cluster.yaml      # Addressing, versions, node inventory — source of truth
│   ├── schematic.yaml    # Image Factory schematic
│   ├── secrets-sops-all.yaml  # Cluster PKI, fully encrypted
│   ├── patches/          # common / controlplane / worker config patches
│   ├── nodes/            # Per-node hardware facts (install disk)
│   └── talos.sh          # Driver: iso, usb, secrets, render, apply, bootstrap
├── pk/                   # Public GPG key material for the SOPS recipients
└── flux/                 # Flux CD configuration — the Kustomization root
    ├── flux-system/      # Bootstrap — do not hand-edit
    ├── infrastructure/   # Cluster-critical: Cilium, CNI, storage, ingress
    ├── platform/         # Services apps depend on: cert-manager, envoy, monitoring
    └── apps/             # User applications
```

## Key conventions

- **SOPS encrypted files** must match pattern `.*-sops\.yaml$` in `.sops.yaml` at repo root. Encrypted keys go under `secrets:` key (matches `encrypted_regex: ^(data|stringData|secrets)$`).
- **RouterOS provider** connects to `https://192.168.1.49` with `insecure = true` (self-signed cert, no IP SANs).
- **Terraform modules** in `modules/` each declare their own `required_providers { routeros {} }` block (no version pin in sub-modules).
- **WireGuard identities** — private keys are under `secrets:` (encrypted), public keys/addresses/ports/endpoint under `identities:` (plaintext). Use `nonsensitive()` on the identities map when iterating peers since Terraform marks the whole `data.sops_file.raw` as sensitive.
- **Firewall rule IDs** — this router uses hex IDs (*A, *B, etc.), numbering starts at *1 (not *0).
- **Firewall rule order** — `modules/ip-firewall` pins every rule with `place_before` pointing at its successor, so table order equals declaration order regardless of when Terraform creates things. Adding a rule means splicing it into that chain.
- **Talos** — `talos/cluster.yaml` is the only place node addresses are written; `talos.sh render` derives hostnames, static addressing, VIP, cert SANs and the installer image from it. Never hand-edit anything in `talos/out/` — it is regenerated and holds decrypted PKI.
- **System extensions are per node, not just per cluster** — `talos/schematic.yaml` is the shared image; a node can add its own under `extensions:` in its `cluster.yaml` entry, and `render` resolves the merged list to a separate Image Factory ID for that node alone. Off-LAN nodes cannot use it — `openstack` builds `edge-0` from the base `out/schematic-id`, so `render` refuses if a WireGuard node lists extensions.
- **A node can carry extra machine config, not just extra extensions** — `patches:` in a node's `cluster.yaml` entry names files under `talos/patches/` that `render` applies to that node alone, between the generated patch and `nodes/<n>.yaml`. Use it when an extension needs config to go with it (gVisor does; kata does not).
- **gVisor runs on cp-0/1/2, like kata** — `siderolabs/gvisor` plus `patches/gvisor.yaml`, which sets `user.max_user_namespaces` (Talos ships it at 0; runsc cannot start without it) and registers a `runsc-netraw` handler running runsc with `--net-raw` and `--allow-packet-socket-write` for Docker-in-pod. The `gvisor` RuntimeClass (`flux/infrastructure/gvisor`) selects the control-plane role. The extension's own flagless `runsc` handler is deliberately left unexposed. Adding gVisor to a node is two reboots: `apply` (the machine config, which cannot go in immediate mode) then `upgrade` (the image).
- **A gVisor or kata pod bypasses Cilium's socket-LB** — the application's `connect()` happens inside the sandbox's own network stack (the runsc sentry, or the kata VM kernel), never as a host syscall, so ClusterIP translation has to come from the tc datapath instead of the cgroup hooks. This cluster has socket-LB off already (`bpf-lb-sock: "false"`, the chart default — the HelmRelease never enables it), so it works; the symptom when it does not is `to-network FORWARDED` in Hubble for a ClusterIP destination and no reply, with pod-to-pod and external traffic unaffected. A `cilium` restart was needed once to make the datapath pick this up.
- **`machine.files` can only `create` under `/var`** — outside `/var` the op must be `overwrite` or `append` on a file that already exists. A failed file write aborts `writeUserFiles`, which halts the boot sequence *before* the kubelet: the node stays reachable over `talosctl` but sits `NotReady` with `/etc/kubernetes` read-only. Fix the config and re-`apply`; no console needed.
- **`/etc/cri/conf.d/20-customization.part` is the only CRI drop-in path Talos accepts** — it is special-cased and injected as a config patch. Any other filename in that directory falls through to the file writer, hits the `/var` rule above, and halts the boot. Everything a node adds to containerd's config shares that one file.
- **Kata Containers runs on cp-0/1/2 only** — `siderolabs/kata-containers` is in those three nodes' extensions, deliberately not `edge-0`'s (no nested virt, and changing its config means Terraform recreating the instance). The extension registers the containerd handlers itself; the `kata` and `kata-qemu` RuntimeClasses live in `flux/infrastructure/kata` and pin scheduling to control-plane nodes so a kata pod cannot land on the edge.
- **Kyverno is installed inert and `platform/kyverno/policies` is where that stops** — the operator registers its resource webhooks *dynamically, from the policies that exist*, so an install with no `ClusterPolicy` intercepts nothing and cannot wedge the API server. The policies therefore live in their own directory under their own Flux Kustomization (`kyverno-policies`, `dependsOn: kyverno`), so suspending or reverting that one directory returns the cluster to the inert state without uninstalling anything. Note the trade the first policy makes: Kyverno's webhooks default to `failurePolicy: Fail`, so while the admission controller is down, pod creation fails in every namespace a policy matches. It stays recoverable only because the chart's default `resourceFilters` exclude the `kyverno` and `kube-system` namespaces outright — Kyverno and the CNI can always restart themselves.
- **The privileged-workload rule is "not unprivileged, but not on the host kernel"** — `require-kata-for-privileged` denies any pod with a privileged container unless its `runtimeClassName` is `kata` or `kata-qemu`, cluster-wide, with `kube-system` (cilium) and `longhorn-system` excluded because both are privileged *in order to* drive the node and are DaemonSets that must run on every node, which the kata RuntimeClass's control-plane `nodeSelector` forbids. gVisor deliberately does not satisfy the rule: the sandbox that matters here is a VM with its own kernel. Adding a namespace to the exclusion list is granting it the right to run privileged on the host — make the argument each time.
- **A `[?…]` filter written directly after a `[]` flatten silently matches nothing** — it is applied *inside* each flattened element instead of to the flattened list, so `length(spec.[containers, initContainers][][?securityContext.privileged == \`true\`])` returns 0 for every pod and a deny rule built on it passes everything while looking right. A `|` before the filter closes the projection first. This was caught by running `kyverno apply` against fixture pods before committing, and is the reason to do that for any new policy — `kyverno jp query -i <pod.yaml> '<expr>'` checks the expression on its own.
- **Extension and version changes need `talos.sh upgrade <node>`, not `apply`** — `machine.install.image` only decides what the next install writes, so a running node keeps its old image until it is upgraded onto the new one. One node at a time; etcd tolerates one of three being away.
- **`-sops-all.yaml` suffix** — encrypts *every* value, not just keys named `secrets`. Required for bundles like the Talos PKI where the sensitive material is not under a `secrets:` key.
- **OpenStack edge-0** — a Talos worker, not a general-purpose VM. Its `user_data` *is* the machine config rendered by `talos/talos.sh render edge-0`; `openstack` defines no cluster config of its own and only reads `talos/` (for the version, schematic ID and rendered config) and the WG registry (for the listen port). There is no cloud-init and no SSH.
- **edge-0 joins over WireGuard only** — the tunnel is declared in the Talos machine config, so it is up before the kubelet starts and the node never contacts the control plane over the bare internet. Its cluster address (`10.200.255.2`) is on `wg0`, not on the cloud NIC.
- **WireGuard addresses are cross-checked** — `talos.sh render` reads `wireguard/identities-sops.yaml` and refuses to render if a node's address there disagrees with `cluster.yaml`. The router derives its routes from the same registry, so a mismatch would produce a tunnel that handshakes and carries nothing.
- **`gen-identity.sh` regenerates the keypair every run** — re-running it for a deployed node invalidates that node's rendered config. Set the endpoint at the same time as the initial key, not afterwards.
- **`network.wg_mtu` in `talos/cluster.yaml` and `MTU` in `flux/infrastructure/cilium/helmrelease.yaml` must move together** (both 1420). Pod payload 1370 + VXLAN 50 exactly fills the tunnel.
- **Flux per-app Kustomizations** — each app gets its own Flux `Kustomization` (a `ks.yaml` in the app directory) that reconciles only that app. No directory-level Kustomization that reconciles everything in `infrastructure/` or `platform/` in one batch.
  - **Organization**: directories (`infrastructure/`, `platform/`, `apps/`) group apps by category, but each subdirectory has its own `ks.yaml`.
  - **Naming**: KS names are flat (`cilium`, not `infrastructure-cilium`). The directory path provides categorization; `dependsOn` chains read naturally (`cert-manager` waits on `cilium`, not `infrastructure-cilium`).
  - **dependsOn**: per-app. `cert-manager` → `dependsOn: [{name: cilium}]`. Apps only wait on what they actually need, not an entire layer.
  - **Adding a new app**: create `platform/<app>/` with `ks.yaml` + `kustomization.yaml` + resources, then add `platform/<app>/ks.yaml` to the root `flux/kustomization.yaml`. The root Kustomization is the only place per-app KS CRDs are collected — not the parent directory.
  - The old directory-level Kustomizations (`infrastructure`, `platform`, `apps`) are deliberately absent. A per-app `cilium` Kustomization replaces them; the `ks.yaml` lives at `infrastructure/cilium/ks.yaml`, not `infrastructure/ks.yaml`.
- **edge-0 taint** — the cloud worker node carries `edge-0=true:NoSchedule`. Applications that tolerate this run on the edge (usually stateless, ingress-terminating workloads). Everything else stays on the LAN nodes by default — no `nodeSelector` needed on every workload.
- **The descheduler balances cp-0/1/2 only, and never touches anything with state** — `platform/descheduler`, a CronJob every 30 minutes (not a Deployment; rebalancing is not latency-sensitive and a one-shot pod costs nothing between runs). Its policy `nodeSelector` is `node-role.kubernetes.io/control-plane`, so edge-0 is outside the calculation entirely — it is tainted and only terminates ingress, and including it would make it look permanently under-utilised while every eviction aimed at it got discarded by `nodeFit` anyway. Balance comes from `LowNodeUtilization` with **`useDeviationThresholds: true`**: the numbers are percentage points from the cluster *average*, not absolute utilisation, which is the only form that does anything on a cluster this lightly loaded — with absolute thresholds every node sits below the low-water mark and nothing is ever moved. Utilisation is read from pod *requests*; real usage would need `metricsUtilization` plus a top-level `metricsProviders` and a `dependsOn` on metrics-server.
- **"Never deschedule the databases" is enforced twice, deliberately** — `PodsWithPVC` in `DefaultEvictor.podProtections.extraEnabled` covers them as a class (and every other Longhorn-backed workload), and a `labelSelector` excluding `cnpg.io/cluster` and `mysql.cnmsql.co/cluster` says it by name. The PVC protection is the one that matters, and what it protects against changed when `longhorn-yolo` moved from `strict-local` to `best-effort`: an eviction used to be merely pointless (the PV's `nodeAffinity` pinned the pod, so it could only restart in place — a failover if it was the primary), and for a volume provisioned under `best-effort` it now genuinely relocates the pod and drags a full replica rebuild across the LAN behind it. Do not weaken it. Note the chart's own default values enable the *opposite* (`defaultDisabled: [PodsWithLocalStorage]`, which is also why `PodsWithLocalStorage` is left at its enabled default here — woodpecker step containers get an emptyDir tmpfs from `woodpecker-docker-tmpfs` and are bare pods with no owner, so an eviction is a failed build with no retry).
- **`RemovePodsViolatingNodeTaints` is deliberately not enabled** — `kubectl cordon` sets `node.kubernetes.io/unschedulable:NoSchedule`, which nothing tolerates, and the descheduler does *not* skip cordoned nodes when choosing eviction *sources* (only when choosing destinations, via `nodeFit`). Enabling the plugin therefore turns every cordon into an unattended drain, including the one `talos.sh upgrade` takes. `nodeFit: true` and `minPodAge: 10m` on the evictor are the other two guard rails, plus per-run caps (`maxNoOfPodsToEvictTotal: 5`, `PerNode: 2`, `PerNamespace: 1`) so a bad policy edit moves a handful of pods before the next reconcile rather than the whole cluster.
- **Envoy Gateway** is the ingress controller (`envoy-gateway` KS). CRDs are installed via the `gateway-crds` Helm chart (`crds.gatewayAPI.channel: experimental` + `crds.envoyGateway.enabled: true`), the controller via the `eg` chart (`install.crds: Skip` since CRDs are managed separately). The proxy (`envoy-proxy` KS) is pinned to `edge-0` via `EnvoyProxy`, uses `externalIPs` to bind the public addresses directly, and terminates TLS with QUIC/HTTP3 listeners. HTTP/HTTPS (TCP 80, 443) plus QUIC (UDP 443) are opened in the OpenStack security group, and TCP 22 for `apps/portfoliosh`.
- **Opening a port on the edge is three separate consents, and two of them fail silently** — the Gateway listener (or a `ListenerSet` attached to it) is only the first. The OpenStack security group in `openstack/main.tf` has to admit the public port, and the `proxy` policy in `platform/envoy-gateway/network-policy.yaml` has to admit `world` on the proxy's *translated* container port (80→10080, 443→10443, 22→10022), because Cilium enforces at the endpoint after the rewrite. Miss either and the listener still reports `Accepted`/`Programmed` with the route attached; the client just hangs on SYN. `hubble observe --verdict DROPPED` on the `edge-0` cilium pod tells the two apart — a packet that never arrives is Neutron, `Policy denied DROPPED` is Cilium.
- **A per-app listener goes in the app's directory as a `ListenerSet`, not in the shared Gateway** — `gateway.networking.k8s.io/v1`, the graduated API; Envoy Gateway 1.8 dropped the experimental `gateway.networking.x-k8s.io/v1alpha1` XListenerSet the root cluster still uses, in the same release it picked up the graduated one. The Gateway must consent: `allowedListeners` defaults to allowing *none*, and `platform/envoy-proxy/gateway.yaml` names the permitted namespaces by label selector rather than `All`, so a new namespace cannot open a public port from its own directory. See `apps/portfoliosh`.
- **external-dns writes the same zones cert-manager solves in** — `platform/external-dns` runs the upstream chart with `M0NsTeRRR/external-dns-webhook-infomaniak` as a webhook-provider sidecar (external-dns talks to it on `localhost:8888`; that is the upstream default, so no `--webhook-provider-url` is set). Sources are `gateway-httproute`, `service` and `crd`; the `DNSEndpoint` CRD comes from the chart's own `crds/`, so the HelmRelease uses `crds: CreateReplace`. `policy: sync` is only safe because of the TXT registry — records without a `k8s-` TXT owned by `ng` are never touched. `domainFilters` is the guard rail: a hostname outside `yewolf.fr`/`hackcorp.net` is silently ignored, not created.
- **The tailnet is shared with the root cluster, so nothing may take a default name** — `platform/tailscale` runs the Tailscale operator (chart `1.98.9`) against the same tailnet the root cluster's `applications/backbone/tailscale` already joined. The operator's own node is named `ng-tailscale-operator` explicitly, because the chart default (`tailscale-operator`) is already taken and a collision is resolved by silently appending `-1` rather than by an error. Tags are shared on purpose: `tag:k8s-operator` for the operator, `tag:k8s` for the proxies, so one set of ACL grants covers both clusters.
- **The OAuth credentials are a precreated Secret, not chart values** — `oauth.clientId`/`oauth.clientSecret` would make the chart template the credentials out of `HelmRelease.spec.values`, which is plaintext in git. Left empty, the operator falls back to mounting a Secret named `operator-oauth` in its namespace, which is `oauth-sops.yaml` (keys `client_id` and `client_secret` — underscores, not camelCase; the chart's own template uses the same names). Use a client distinct from the root cluster's so either can be revoked alone.
- **Cross-cluster access is two objects in two repos** — the side that owns the workload publishes it (a `Service` with `loadBalancerClass: tailscale`, or the `tailscale.com/expose` annotation), and the side that consumes it declares an `ExternalName` Service annotated `tailscale.com/tailnet-fqdn: <host>.<tailnet>.ts.net` with a placeholder `externalName` the operator overwrites. Neither half works alone: the consumer's ExternalName resolves to nothing until the publisher's proxy has registered. This is the path for pulling data out of the root cluster's databases into `ng` — root publishes `postgres-rw`/`mysql`, `ng` consumes them under a Service name the migration job dials.
- **A tailscale `Ingress` takes its hostname from `tls.hosts`, not from a rule host** — `apps/radar` is exposed as `radar`, and the only place that name appears is `spec.tls[0].hosts`. The chart's own ingress cannot express that, which is why `ingress.enabled: false` and the Ingress is a hand-written file. Renaming one later is not just a git edit: the old device lingers in the tailnet until it is deleted from the admin console, and the new name gets a `-1` suffix while it does. That is what the `-ng` suffixes were for — `radar-ng`, `qbittorrent-ng`, `joal-ng`, `scrutiny-ng`, `longhorn-ng` — while the root cluster still held those names on the shared tailnet. Those devices are deleted and the suffixes are off, but the collision rule has not changed: a *new* name the root cluster still holds still needs one.
- **Radar is unauthenticated on purpose and the tailnet is its only access control** — `auth.mode: none` with `rbac.helm`, `podExec` and `portForward` all on, so anything that can reach port 9280 can exec into any pod and drive Helm. Its network policy therefore admits ingress *only* from the `tailscale` namespace; that ingress rule is a security control, not tidiness. `rbac.crdGroups.all: true` for the same "private tailnet" reason — the chart's per-group list predates longhorn.io, barmancloud.cnpg.io, mysql.cnmsql.co and tailscale.com, so the alternative is editing `additionalCrdGroups` every time an operator lands.
- **`toFQDNs` cannot express DERP, so both tailscale policies open `world` on 443** — Cilium learns an FQDN's addresses by inspecting DNS answers, but tailscaled receives the relay list as a *derpmap* over its control-plane connection and dials those nodes by literal IP. No lookup happens for Cilium to observe, so a `*.tailscale.com` rule matches nothing and every relay is dropped: dozens of `Policy denied DROPPED (TCP Flags: SYN)` to assorted :443 addresses, from both the operator and the proxies, while the pod looks healthy. Pinning a `toCIDRSet` is not the fix either — the relay set rotates. This was tried the narrow way first and it does not work.
- **Both tailscale policies also need UDP to `world` on every port** — STUN to the relays, then WireGuard direct to whatever ip:port a peer turns out to be behind, neither knowable in advance. Unlike the 443 rule, restricting this does not produce drops that stop anything: it silently demotes the tunnel to relaying every byte through DERP.
- **The operator is a tailnet node, not just an API client** — so it probes and holds a DERP home relay exactly like a proxy does, and its policy ends up nearly identical to `tailscale-proxies`. The two are kept separate for their ingress rules and their selectors: `app: operator` versus `tailscale.com/managed: "true"`, which is the only label a proxy carries that does not name the Service it was created for. The proxies also talk to the apiserver because tailscaled keeps its node state in a Secret rather than on disk.
- **The API server proxy is off** (`apiServerProxyConfig.mode: "false"`) — cluster admin already comes over WireGuard from the LAN, and turning it on would put the apiserver on the tailnet behind a separate authorization path.
- **KEDA is two HelmReleases in one Kustomization** — `platform/keda` runs the `keda` chart (operator, metrics adapter, admission webhooks) and `keda-add-ons-http` (HTTP scale-to-zero), both in the `keda` namespace; the add-on `dependsOn` the core release because its CRD controller needs KEDA's `ScaledObject` API. `interceptor.replicas.min` stays at 1 — the interceptor scaling to zero would black-hole the wake-up request itself. Six CiliumNetworkPolicies cover the six workloads; none of them may reach `world`, so a trigger against a cloud API (SQS, Service Bus) needs a `toFQDNs` rule added to `keda-operator`. Two `toEntities: [cluster]` egress rules are deliberately loose because their targets are user-defined: the operator dials whatever scaler a `ScaledObject` names, and the interceptor forwards to whatever Service an `InterceptorRoute` names.
- **HTTP scale-to-zero is three objects, not one** — this cluster uses `InterceptorRoute` (`http.keda.sh/v1beta1`) + a plain KEDA `ScaledObject`, not the older all-in-one `HTTPScaledObject` the root cluster still runs. The `InterceptorRoute` carries routing and the scaling *metric* but no replica counts; the `ScaledObject` carries `minReplicaCount: 0` and an `external-push` trigger whose `interceptorRoute` metadata **must equal the InterceptorRoute's `metadata.name`**. Get that name wrong, or let the `ScaledObject` reconcile before the route exists, and the scaler returns an empty metric spec — the HPA then silently falls back to a CPU metric and the app never wakes, with no error anywhere. The third object is the `HTTPRoute`, whose `backendRef` is `keda-add-ons-http-interceptor-proxy:8080` in `keda`, never the app's own Service; the `InterceptorRoute` picks the real backend off the Host header. See `apps/cyberchef`.
- **A cross-namespace `backendRef` needs consent from the namespace being pointed at** — so the `ReferenceGrant` for every scale-to-zero app lives in `platform/keda/reference-grants.yaml`, not in the app's own directory. Adding an app means adding a grant there too, or the route attaches and returns 500 with no obvious cause. Same pattern as `platform/certificates/reference-grant.yaml` for the Gateway's cross-namespace `certificateRefs`.
- **`booting-up` is the shared cold-start placeholder** — a Caddy serving one self-refreshing page from a ConfigMap. An app opts in via `coldStart.fallback` on its `InterceptorRoute`, which resolves Service names in the *app's own* namespace, so each app also carries a `service-fallback` `ExternalName` aliasing `caddy.booting-up.svc.cluster.local`. Pair it with a short `timeouts.readiness` (cyberchef uses 2s): that value is how long a request hangs before it gets the placeholder instead. The page polls `/is_still_booting_up`, which keeps hitting the placeholder until the real pod is ready and then reloads.
- **Two database operators, both cluster-wide** — `platform/cnpg` (CloudNativePG, Postgres) and `platform/cnmsql` (CNMSQL, Percona Server for MySQL / MariaDB; upstream is `github.com/cnmsql/cnmsql`, docs at `cnmsql.co`). Both run with cluster-scoped RBAC (`config.clusterWide` / `rbac.namespaced: false`), so a `Cluster` is declared in the *app's* namespace, not the operator's. Their network policies end in `toEntities: [cluster]` for the same unavoidable reason KEDA's do — the instance pods they drive can be anywhere. Neither operator reaches `world`: backups and WAL/binlog archiving to S3 are the *instance* pods' egress, and those pods get their own policy in the app's directory.
- **CNPG and CNMSQL get their webhook certs differently** — CNPG's operator issues and rotates its own, so its KS only `dependsOn` `cilium`. CNMSQL's chart creates a self-signed cert-manager `Issuer` plus `Certificate`s and leans on cainjector for the webhook `caBundle`, so its KS `dependsOn` `cert-manager` — reconcile it before cert-manager is ready and the webhook stays certless and every `Cluster` apply is rejected.
- **CNMSQL ships no HTTP Helm repository** — the chart is GHCR-only (`oci://ghcr.io/cnmsql/charts/cnmsql`), so it uses an `OCIRepository` + `chartRef` like `envoy-gateway`, not the `HelmRepository` + `chart.spec` form the other platform apps use. Renovate's `flux` manager reads `OCIRepository.spec.ref.tag`, so it is still pinned and still bumped.
- **Longhorn has two disks per node, deliberately kept as two pools** — `patches/longhorn.yaml` (on cp-0/1/2) declares `UserVolumeConfig longhorn`, a fixed 100 GiB partition of the system NVMe at `/var/mnt/longhorn` (tag `nvme`), and `UserVolumeConfig longhorn-ssd`, the whole 256 GB Netac SATA SSD at `/var/mnt/longhorn-ssd` (tag `sata`, ~238 GiB). They are not interchangeable and merging them would throw that away: the NVMe is faster but is the device etcd fsyncs to, so sustained churn on it competes with the control plane at the queue, not just at the filesystem; the Netac contends with nothing. Every StorageClass therefore carries a `diskSelector` — `longhorn-yolo` takes `nvme` (the databases: one replica, latency is the whole point of that class), `longhorn`/`longhorn-ha`/`longhorn-ci` take `sata`. Neither pool is a directory on `EPHEMERAL`, which is what the whole arrangement exists to avoid — replica data there competes with container images and logs, and either one filling the filesystem takes the kubelet with it. The kubelet needs the `extraMounts` bind with `rshared` for both paths: without the propagation flag the per-volume mounts Longhorn creates never reach the pods that asked for them, and `statfs` reports `EPHEMERAL`'s free space for the disk.
- **The disk list is declared in Talos, not by hand or by `defaultDataPath`** — `machine.nodeLabels: node.longhorn.io/create-default-disk: config` plus `machine.nodeAnnotations: node.longhorn.io/default-disks-config` (a JSON array of paths, `allowScheduling` and tags), paired with `createDefaultDiskLabeledNodes: true` in the HelmRelease. So the disks a node mounts and the disks Longhorn schedules onto come from one file, with their tags. A node *without* the label gets no disks at all, which is the enforceable half of "edge-0 is not a storage node" — the taint and the `nodeSelector`s are the other two. **Registration-time only**: neither the label nor the annotation touches a node Longhorn already knows about, whose disks are a list on its `nodes.longhorn.io` object, so the three existing nodes were patched by hand once (procedure in `talos/README.md`). `defaultDataPath` is now only reachable for a node labelled `true` rather than `config`, i.e. never — but leave it pointing at a real mount, because unset it falls back to `/var/lib/longhorn` on `EPHEMERAL`.
- **The Netac is selected by model, never by device name** — `disk.transport == "sata" && disk.model == "Netac SSD 256GB"`. `sda` is whatever the SATA controller enumerated this boot and is also what a USB installer takes while plugged in, and the Netac is the same nominal size as the system NVMe, so size is no discriminator either. A model string that stops matching is a volume that never provisions (loud); a selector that matches too broadly is a wiped disk.
- **`fromEntities: kube-apiserver` never matches an admission webhook call in this cluster** — the API server is host-networked on the control planes, and its connection into the pod network enters via the calling node's `cilium_host` router address (`10.244.<n>.<x>`). The identity Cilium evaluates at the destination is therefore `reserved:host` when the API server and the target pod share a node, or `reserved:remote-node` for the other two — never `reserved:kube-apiserver`. Every policy fronting a webhook or an aggregated APIService needs `remote-node` and `host` spelled out. **The failure is partial, which is why these survive**: the same-node third works (Cilium auto-allows `host` to local pods), so the thing looks healthy, an APIService can report `Available=True`, and only two calls in three are dropped. Confirm with `hubble observe --verdict DROPPED --to-port <port>` on the *destination* pod's node — the drop is `Policy denied DROPPED (TCP Flags: SYN)` from a `10.244.x.y (remote-node)` source. Audited 2026-07-28: `cnmsql`, `keda-operator-metrics-apiserver` and `keda-admission-webhooks` were broken and are fixed; `cnpg` was already safe via `cluster`; `cert-manager` and `external-secrets` already named the entities. `kyverno` and `longhorn` were safe only *incidentally*, via a port-unrestricted `[host, remote-node, health]` probe rule that happens to cover the webhook port — scoping that rule to the probe ports would silently cut the webhook off, so both files now say so.
- **The interesting half of that bug is how it fails, not that it fails** — `failurePolicy` decides which symptom you get, and neither points at the network. Kyverno's resource webhook is `Fail`, so a drop is a hard cluster-wide outage. KEDA's ScaledObject webhook is `Ignore`, so every write blocked the full 10s admission timeout and was then **admitted with its validation skipped** — a successful `kubectl apply` that took ten seconds and checked nothing. cnmsql's is `Fail` and took the operator down with it: every reconcile blocked on the timeout, the controller-runtime worker pool saturated, `/healthz` stopped answering and the kubelet killed the pod on its liveness probe — **exit 137, which reads like an OOM and is not one** (the termination reason is `Error`, not `OOMKilled`, and the pod was using 50Mi of a 512Mi limit). Check the terminated reason and actual usage before raising a memory limit.
- **PodSecurity `enforce: baseline` is on cluster-wide, and it is not Kyverno** — it comes from the API server's `admissionControl` block in `talos/out/base/controlplane.yaml` (`audit`/`warn: restricted`, `enforce: baseline`, exemptions: `kube-system` only). Practical consequence: **a pod that adds any capability is refused outright**, including the `NET_RAW` that ping-style workloads want (this is why `apps/uptime-kuma` drops it and the root cluster's copy did not have to). The failure is easy to misread — the Deployment applies cleanly and reports `0/1`, and the refusal is only visible as `FailedCreate` events on the *ReplicaSet*, never on the Deployment or a pod. `warn: restricted` also means a perfectly legal pod can print a scary two-line warning on `kubectl apply` and still be admitted; satisfying it is usually just `runAsNonRoot: true`. Relaxing it for one workload is a `pod-security.kubernetes.io/enforce` label on that namespace, never a change to the Talos config.
- **etcd snapshots are `platform/talos-backup`, and the key that decrypts them is deliberately unreachable from the cluster** — `siderolabs/talos-backup` on a CronJob every six hours: snapshot over the Talos API, zstd, age-encrypt, push to `s3://default/etcd` on its own Swiss Backup tenant. The encryption is asymmetric on purpose. The recipient (`AGE_RECIPIENT_PUBLIC_KEY`) is public and sits in plaintext in `cronjob.yaml` and `talos/etcd-backup-age.pub`; the private half is `talos/etcd-backup-age-sops-all.yaml`, which lives under `talos/` rather than `flux/` for one reason — anything under `flux/` that a Kustomization points at gets decrypted by kustomize-controller and materialised as a Secret, which would put the key that reads every backup inside the cluster the backups exist to recover. The job can write snapshots it cannot read; keep it that way. Restore is `age -d -i` on a laptop, then `talosctl bootstrap --recover-from=`. Only one recipient is configured so far, and `AGE_RECIPIENT_PUBLIC_KEY` is a comma-separated list — a second key held elsewhere is the obvious next step. **The image is a commit build of main, not the `v0.1.0-beta.3` release tag, and must stay that way** — that tag is from 2024-08 and reads `AGE_X25519_PUBLIC_KEY` rather than the `AGE_RECIPIENT_PUBLIC_KEY` its own `cronjob.sample.yaml` documents, has no compression at all, and parses `UsePathStyle` as `== "false"` (inverted, so `USE_PATH_STYLE=true` silently selects virtual-host addressing and misses both the endpoint and the single-FQDN network policy). The key-name mismatch fails *after* the etcd read — `malformed recipient ""` — so it looks like a working backup right up until you read the log.
- **Retention is a second CronJob because Swiss Backup has no lifecycle API** — talos-backup uploads and never deletes, and the normal answer (an S3 lifecycle rule on the bucket) is not available: `GET /default?lifecycle` against `s3.swiss-backup02.infomaniak.com` returns **200 with a plain `ListBucketResult`**. The subresource is not rejected, it is *ignored*, and the request falls through to a bucket listing — Swift s3api behaviour. A lifecycle rule written there would look like it applied and do nothing, which is worse than an error, so do not try again on the assumption it was misconfigured. `talos-backup-prune` instead runs `rclone delete sb:default/etcd --min-age 7d` daily at 05:40, deliberately between the 00:00 and 06:00 backup slots. Its rclone remote is defined entirely in env vars, so there is no config file and no credential on disk. The path must track `BUCKET`/`S3_PREFIX` in `cronjob.yaml`; on drift it deletes nothing rather than the wrong thing, but a silently-idle prune looks exactly like one with no work to do.
- **The network policy is split in two, and that split is the point** — `talos-backup` selects the whole namespace (DNS + the one S3 FQDN, which both workloads need), while `talos-backup-api` selects `app.kubernetes.io/name: talos-backup` alone and is the only thing granting apid on 50000. Cilium unions egress across policies selecting an endpoint, so the backup pod gets both and the prune pod gets only the baseline. Do not fold them back together: the prune job runs a third-party binary with write access over the whole bucket and has no business reaching the Talos API.
- **The credential the backup job holds is minted by the cluster, not taken from the PKI** — `machine.features.kubernetesTalosAPIAccess` in `patches/controlplane.yaml` registers the `serviceaccounts.talos.dev` CRD, and a control-plane controller turns each `talos.dev/v1alpha1` ServiceAccount in an *allowed namespace* into a Secret holding a talosconfig scoped to the roles it asked for. So `talos/secrets-sops-all.yaml` is never involved and the credential rotates itself. Two things fail silently: a namespace missing from `allowedKubernetesNamespaces` means the Secret is simply never created (the pod hangs on the missing volume, with no event explaining why), and the KS `dependsOn` cannot express the CRD — it comes from a machine config that has to be `apply`ed first, so reconciling before that gives an unknown-kind error no ordering can fix. The role list is cluster-wide, not per-namespace: adding to `allowedRoles` widens what *every* allowed namespace can request.
- **The backup pod needs no `nodeSelector`, and its network policy says `host`/`remote-node` rather than naming a Service** — the generated talosconfig points at `talos.default:50000`, a *selectorless* Service whose EndpointSlices Talos fills with the control-plane node addresses. With socket-LB off (as it is here), the ClusterIP is translated in the tc datapath, so by the time Cilium evaluates policy the destination carries a node identity and a `toEndpoints` or `toServices` rule matches nothing. Same shape as the Longhorn and postgres policies for S3: one `toFQDNs` for `s3.swiss-backup02.infomaniak.com` plus the DNS rule with `rules.dns` — without L7 DNS visibility the FQDN entry never populates and every upload is dropped while the name still resolves fine from inside the pod.
- **The two pools are added to a live node in completely different ways, and that is the argument for the second disk** — the `sata` pool is a blank disk, so nothing has to be repartitioned around it and adding it is a plain `apply` with no reboot. The `nvme` pool is carved out of the system disk, and Talos applies volume sizing **only at provisioning time**: `EPHEMERAL` already fills that disk, the `maxSize` cap is ignored rather than enforced, and the partition only appears after `talosctl reset --system-labels-to-wipe EPHEMERAL --graceful --reboot` per node with an etcd quorum wait in between. Do not carve anything further out of the system disk.
- **`diskSelector` is stamped onto a volume at provisioning time**, like `reclaimPolicy` — so tagging the disks moved nothing. The four Postgres/MySQL volumes were already on the NVMe, which is where `longhorn-yolo` wants them, so they never moved. Everything provisioned from now on lands on the pool its class names.
- **Vaultwarden was migrated `nvme` → `sata` by copy-and-rebind, not by disk eviction** — procedure in `talos/README.md` ("Moving an existing volume between pools"). `evictionRequested: true` is the obvious tool and was not used: it evicts a whole *disk* rather than one volume, and with `replicaSoftAntiAffinity: false` the rebuild must place a second replica on a node that already holds one, so whether it moves anything turns on Longhorn discounting an already-evicting replica. Instead: suspend the Kustomization, scale to zero, provision a second PVC on the target class, `cp -a` between them in a Job that mounts both (uid 0, so ownership survives; verify with `sha256sum -c`, do not trust the exit code), delete both PVCs, then overwrite the new PV's `claimRef` with a uid-less reference to the *original* claim name. That last step is the trick — reserving the PV rather than pinning the PVC with `volumeName` keeps `pvc.yaml` free of a cluster-specific volume ID, so Flux recreates the claim from the unchanged manifest and it binds to the right PV anyway. `Retain` on both classes is what makes every step reversible; the old PV is left `Released` with its `claimRef` intact as the rollback, and deleting it is a separate, later decision.
- **A StorageClass is immutable in every field that matters, so the `longhorn` Kustomization carries `force: true`** — `parameters`, `provisioner`, `reclaimPolicy` and `volumeBindingMode` all reject updates with `field is immutable`, which fails the apply and wedges the entire Kustomization until someone deletes the object by hand. `force` makes Flux delete and recreate on that error only. It is safe here because a PV records its own parameters at provisioning time and references the class by name alone — recreating the class is invisible to every volume that already exists, and steers new claims only, which is what the edit was for. `kubectl apply --dry-run=server` is what settles whether a given field is immutable; it runs the real admission chain.
- **Three StorageClasses, all declared by hand** — `longhorn` (3 replicas, the default class), `longhorn-ha` (2), `longhorn-yolo` (1), in `flux/infrastructure/longhorn/storageclasses.yaml` with the chart's `persistence.createStorageClass: false`. The chart can only express one class, and it does so via a ConfigMap that longhorn-manager converts into the real object — so leaving it on would describe the default class in a different form and a different file from the two beside it. The three differ only in replica count, `dataLocality` and which disk pool their `diskSelector` names.
- **All three are `reclaimPolicy: Retain`, deliberately** — the chart default is `Delete`, which makes deleting a PVC (by hand, or by Flux pruning, or by a chart being uninstalled) an unrecoverable data loss with no confirmation step. The cost is that retained volumes are not garbage-collected: a deleted PVC leaves a `Released` PV and a Longhorn volume occupying the 100 GiB budget forever, so `kubectl get pv | grep Released` is real housekeeping and exhausting the partition will present as a provisioning failure rather than as a pile of orphans. Retain also does *not* mean "reattaches next time" — a `Released` PV keeps a `claimRef` to the vanished PVC and will not bind to a new one, so recreating the app gets a fresh empty volume until someone clears `.spec.claimRef` by hand. `reclaimPolicy` is stamped onto a PV at provisioning time, so changing it in a StorageClass only affects volumes created afterwards.
- **`volumeBindingMode: WaitForFirstConsumer` on all three** is the part of "run the workload where its data is" that Kubernetes actually enforces — provisioning waits for the pod to be scheduled, so replicas are placed around the chosen node instead of the pod being drawn to a volume provisioned arbitrarily at apply time. `dataLocality` covers the rest, and only `strict-local` (now just `longhorn-ci`) truly pins scheduling, because a Longhorn v1 volume is network-reachable from any node and so no other class's PV carries `nodeAffinity`. `longhorn` sets `dataLocality: disabled` deliberately: 3 replicas + `replicaSoftAntiAffinity: false` + exactly 3 storage nodes means every node already holds a replica and `best-effort` would have nothing to do.
- **`longhorn-yolo` is `best-effort`, not `strict-local`, and the reason is maintenance** — `strict-local` writes a hard `nodeAffinity` onto the PV, so `kubectl drain` (i.e. `talos.sh upgrade`) evicts the database pod and it then sits `Pending`, because the only node it may run on is the one just cordoned; that instance is down for the whole window. `best-effort` writes no `nodeAffinity`, so the pod reschedules, attaches over the network to the replica on the cordoned-but-running node, and Longhorn rebuilds a local replica behind it — a CNPG failover instead of a stall. The price is that a pod which moves drags a full replica rebuild across the LAN, which is what makes the descheduler's `PodsWithPVC` protection load-bearing rather than merely pointless. It does **not** fix the drain block itself: that is `numberOfReplicas: 1` against Longhorn's `block-if-contains-last-replica`, and one replica is always the last one.
- **`longhorn-ci` keeps `strict-local` deliberately** — a woodpecker workspace is created by the first step of a pipeline and deleted by the last, and the step pods are bare pods with no owner, so there is no rescheduling for `best-effort` to enable and local I/O for image builds is worth more.
- **`dataLocality` steers new volumes only, and a PV's `nodeAffinity` is immutable once written** — so the four database volumes provisioned while `longhorn-yolo` was `strict-local` are still pinned (`postgres-1`/`mysql-1` → cp-2, `postgres-2`/`mysql-2` → cp-1), and patching `Volume.spec.dataLocality` on them will not unpin the PV. Unpinning one means recreating the claim: for CNPG and CNMSQL, deleting the instance and letting the operator re-clone from the primary. `strict-local` also needs exactly one replica — Longhorn rejects creation otherwise — and does not support RWX. Never add `allowedTopologies` to a Longhorn class: the PV `nodeAffinity` it produces is immutable and collides with Longhorn's own pinning.
- **`longhorn-ci` is the fourth class and the only `reclaimPolicy: Delete` one** — identical to `longhorn-yolo` apart from that and the pool: it is on `sata`, because a build cache is the last thing that should share a device with etcd. It exists for woodpecker, whose Kubernetes backend provisions a workspace PVC per pipeline and deletes it at the end: under Retain every build would leave a `Released` PV and a Longhorn volume out of the pool with nothing to reclaim them. Never point a stateful app at it because the name sounds fast — the reclaim policy is stamped onto the PV at provisioning time, so a database on this class is one `kubectl delete pvc` from gone.
- **Longhorn's network policy selects the whole namespace, on purpose** — only `longhorn-manager`, `longhorn-driver-deployer` and `longhorn-ui` come from the chart. The instance managers, the CSI plugin and its sidecars, the share managers and the backing-image managers are created at runtime with labels that depend on which volumes exist, so a per-workload `endpointSelector` would cover the three static pods and default-deny everything that actually moves replica data. Engine-to-replica traffic uses dynamic ports in the 10000-30000 range, which is why the intra-namespace rule is portless. Nothing reaches `world` — `upgradeChecker` is off for that reason, and configuring an S3 backup target later is what would need a `toFQDNs` rule added.
- **edge-0 is not a storage node** — it has no Longhorn disk, and replicating over the WireGuard tunnel to Infomaniak would be slow. Its `edge-0=true:NoSchedule` taint already keeps Longhorn off it, but every component also carries a control-plane `nodeSelector` so that an untainted worker added later does not silently become a storage node. Stateful workloads therefore stay on the LAN hosts.
- **There is one Postgres for the whole cluster** — `platform/postgres`, a two-instance CNPG `Cluster` in the `postgres` namespace. Apps do not get their own instance; they get a database on this one, declared with a `Database` CR **in the app's own namespace** pointing at `cluster: postgres`. That cross-namespace reference only works because `platform/cnpg` runs with `config.clusterWide: true`. Connection endpoints are `postgres-rw` (primary, writes), `postgres-ro` (standby, reads) and `postgres-r` (any instance), all in `postgres`.
- **Replication is async and that is deliberate at two instances** — a synchronous standby that goes away blocks every write on the primary, which would turn "one node is down" from survivable into a total outage. The cost is a bounded window of transactions that exist only on the primary if it dies abruptly. Anti-affinity is `required`, not the default `preferred`: two instances on one node is two copies on one disk and a replica pair that dies together.
- **VectorChord needs a CNPG-derived image, not just any Postgres image with the extension** — `ghcr.io/tensorchord/cloudnative-vectorchord` is built *from* the official CNPG image, so it keeps barman-cloud, the instance-manager entrypoint and the uid-26 postgres user. `tensorchord/vchord-postgres` and `vchord-suite` are built on the upstream postgres image and CNPG cannot drive them — they are not drop-in substitutes. Tag format is `<postgres>-<vectorchord>` (currently `18.4-1.1.1`).
- **`vchord.so` must be in `shared_preload_libraries`** — CREATE EXTENSION alone is not enough, the background workers load at startup and the extension fails at query time without it. Changing that list restarts the cluster.
- **`CREATE EXTENSION vchord` goes in `postInitTemplateSQL`, not `postInitApplicationSQL`** — template1 is what every later database is cloned from, so putting it there makes vchord present in every app database automatically instead of each app having to remember. `CASCADE` pulls in pgvector, which vchord builds on and the image ships. Bootstrap SQL runs **exactly once, at cluster creation**: editing it later does nothing to a running cluster, and an existing database would need the extension added by hand or via the `extensions` field on its own `Database` CR.
- **Postgres uses `longhorn-yolo` on purpose** — CNPG already keeps a second copy on the other instance, so a 3-replica class would write six copies of every transaction to protect against a failure CNPG already handles, and `best-effort` locality keeps Postgres reads and writes off the network whenever the replica can be local — which is always, except while a rebuild is catching up after the pod has moved. The trade is that losing a node's disk destroys that instance outright; the recovery is CNPG re-cloning it from the survivor, which is what the second instance is for.
- **There are no Postgres backups yet** — no `backup:` stanza, because `ng` has no S3 target at all. Two instances cover node loss; they do not cover `DROP TABLE`, corruption replicating to the standby, or losing the cluster, and every app's data is on this one Postgres. Closing it is a `backup.barmanObjectStore` block, a credentials Secret, a `ScheduledBackup`, and a `toFQDNs` egress rule in its network policy — `world` is denied outright today.
- **There is one MySQL for the whole cluster too** — `platform/mysql`, a two-instance CNMSQL `Cluster` (`mysql.cnmsql.co/v1alpha1`, note the group is *not* `cnmsql.co`) in the `mysql` namespace, deliberately the same shape as `platform/postgres`. Percona Server for MySQL 8.4. Apps get a database via a `Database` CR; that works across namespaces because `platform/cnmsql` sets `rbac.namespaced: false`.
- **Database tenancy is declared in the *database's* directory, not the app's** — `platform/postgres/applications/<app>/` and `platform/mysql/applications/<app>/`, each with its own flat `ks.yaml` (`<app>-db`) listed in `flux/kustomization.yaml`. The CRs live in the `postgres`/`mysql` namespace; only the credentials cross into the app's, via an ESO `PushSecret` + `SecretStore` + a per-app `eso-push-writer-<app>` ServiceAccount whose RoleBinding sits at the far end. **One SA per app, never a shared one** — sharing would make one directory depend on another applying first, and a `SecretStore` naming an SA it was not granted fails validation with the unhelpful "client is not allowed to get secrets". This is also why the app's own `ks.yaml` does *not* `dependsOn` the `-db` one: the `-db` Kustomization writes a Role into the app's namespace, so it is the half that waits.
- **`apps/uptime-kuma` is the first MySQL tenant, and it is someone else's** — Uptime Kuma run for @nounoursdestavernes, migrated off the root cluster's MariaDB 2026-07-30. Namespace `nounoursdestavernes` (named for the tenant, not the workload — it is the one namespace whose contents are driven from a UI nobody here controls), database `nounoursdestavernes_uptime`, public at `uptime-aurelien.yewolf.fr`. Its egress policy is `0.0.0.0/0` + `::/0` **minus the private ranges**, and that carve-out is a security control, not tidiness: a monitor is an arbitrary URL, so without it "monitor `http://10.244.0.5:8080`" is a working port scanner aimed at the pod network, the node LAN and the tailnet. Both address families, because pods here are dual-stack and Node returns AAAA first.
- **A MariaDB dump does not load into MySQL 8.4 unmodified, and both blockers are in the DDL** — (1) every table carries `COLLATE=utf8mb4_uca1400_ai_ci`, a MariaDB-only UCA-14.0.0 collation MySQL rejects outright; rewrite to `utf8mb4_0900_ai_ci`, the closest equivalent (also UCA, also accent- and case-insensitive). (2) MariaDB permits literal defaults on `TEXT`/`BLOB`/`JSON` columns and MySQL does not — `text NOT NULL DEFAULT '[]'` fails with "BLOB, TEXT, GEOMETRY or JSON column ... can't have a default value". `DEFAULT NULL` is fine; only non-NULL literals break, and the fix is MySQL 8's expression-default form, `DEFAULT ('[]')`, which preserves the semantics. Neither shows up until the restore is half-applied, so grep the dump first. `int(10)` display widths, `current_timestamp()` and `/*M!…*/` comments all pass through harmlessly, and the remaining databases in `migrate/dumps/…/mariadb-all.sql.gz` (`bm`, `matomo`, `pterodactyl`) will hit exactly the same two.
- **`on:` is a YAML 1.1 boolean, and `DatabaseUser.spec.grants[].on` is the field that trips on it** — unquoted, it parses as `true`, and the API server rejects the object with `strict decoding error: unknown field "spec.grants[0].true"`, which does not obviously point at quoting. Write `"on":`.
- **Prefer underscores to hyphens in MySQL database and user names** — `grants[].on` is interpolated straight into a `GRANT` statement, so a hyphenated name is a syntax error unless the operator quotes it, which is not worth finding out at reconcile time. The root cluster's `uptime-aurelien` became `nounoursdestavernes_uptime` for that reason. MySQL user names also cap at 32 characters, which a long tenant-prefixed name can reach.
- **CNMSQL needs its own instance image, like CNPG does** — `ghcr.io/cnmsql/cnmsql-instance:8.4-4`, not stock `percona/percona-server`. The operator drives an instance manager that has to be present in the image. The tag is `<series>-<build>`; `8.4-4` is what the floating `8.4` resolved to when it was pinned. **amd64 only**, so it can only run on cp-0/1/2 anyway.
- **`flavor` and `replication.mode` are both immutable after creation** — changing either means rebuilding the cluster and restoring from a dump, so both are stated explicitly rather than left to their defaults.
- **MySQL is async + semi-sync, not Group Replication, because there are two instances** — a Group Replication group needs an odd member count to hold a quorum, so a two-member group cannot form one after losing a member, which is the exact failure it would exist to survive. Quorum would mean `instances: 3`. Instead `mysql.semiSync.enabled: true` makes the primary wait for the replica to acknowledge a commit, with **`dataDurability: preferred`** doing the important work: under `required` the ack count is fixed and a downed replica blocks every write until it returns, while `preferred` self-heals the count down to the healthy replica count so the pair degrades to async and stays writable. `maxSyncReplicas` must stay below `instances`, so this pair can only ever be 1/1.
- **`binlogFormat: ROW` is not optional** — it is the only format safe for both replication and PITR; `STATEMENT` silently diverges the replica on any non-deterministic statement.
- **MySQL bootstraps `utf8mb4`/`utf8mb4_0900_ai_ci` explicitly** — MySQL's historical `utf8` is a three-byte subset that cannot store emoji or much of CJK, and the mistake only surfaces later as data that will not insert.
- **Postgres backups go through the Barman Cloud plugin, never the in-tree `spec.backup.barmanObjectStore`** — the in-tree integration has been deprecated since CNPG 1.26 and was *slated for removal in 1.30*, which is the version running here. It survived, and the schema is still in the CRD, so it will silently accept configuration — but building on it means a forced migration on some future operator bump, found out during a restore. `platform/barman-plugin` installs the plugin (OCIRepository + HelmRelease, chart `0.7.0` = appVersion `v0.13.0`) into **cnpg-system**, which is mandatory: CNPG discovers the plugin over a Service in its own namespace. The destination is an `ObjectStore` CR (`barmancloud.cnpg.io/v1`) in the `postgres` namespace, referenced from `Cluster.spec.plugins` with `isWALArchiver: true` and from the `ScheduledBackup` via `method: plugin`. All three `barmanObjectName` values must name the same ObjectStore.
- **The barman plugin's network policy is split across two namespaces, deliberately** — the plugin Deployment in `cnpg-system` never uploads anything; it hands configuration to a sidecar the operator injects into each Postgres instance pod. So the `toFQDNs` rule for the bucket lives in `platform/postgres/network-policy.yaml`, next to the pods that actually talk to S3, and `platform/barman-plugin/network-policy.yaml` has no `world` egress at all. The instance pods also need egress to the plugin on 9090 (CNPG-I gRPC).
- **`wal.compression` and `data.compression` do not accept the same codecs** — WAL allows `bzip2/gzip/lz4/snappy/xz/zstd`, data allows only `bzip2/gzip/lz4/snappy`. `zstd` under `data` is rejected by the CRD. This cluster uses `zstd` for WAL (higher volume, latency-sensitive) and `gzip` for base backups (bottleneck is bytes on a home uplink, not CPU).
- **The two databases back up to two different Infomaniak accounts, not two prefixes in one bucket** — Postgres to `sb_project_SBI-TS165990`, MySQL to `sb_project_SBI-TS538856`. Neither set of credentials can read or delete the other's archive. Both use bucket `default` with a `/postgres` or `/mysql` prefix, which is tidiness rather than isolation.
- **CNPG's `ScheduledBackup` schedule also has six fields** — same seconds-first gotcha as CNMSQL's. Postgres runs at `"0 30 3 * * *"` (03:30), an hour after MySQL's 02:30, so the two are not competing for the same disks and uplink.
- **MySQL backs up natively; CNMSQL has no plugin split** — `platform/mysql` uses `backup.objectStore` directly on the Cluster (bucket `default`, prefix `/mysql`, region `us-east-1`, path-style, credentials from the SOPS-encrypted `mysql-backup-s3` Secret). `continuousArchiving` ships binlogs (`targetRPOSeconds: 300`) and a `ScheduledBackup` takes a nightly xtrabackup base backup from the standby, 30d retention on both. This is *not* the deprecated shape — it is CNMSQL's own current API, unrelated to CNPG's in-tree barman deprecation.
- **`backup.reclaimPolicy` defaults to `Retain` and should stay there** — `Delete` attaches a finalizer that wipes the *entire* archive (every base backup, every binlog, the index) when the Cluster is deleted, which is the same class of unpleasant surprise the `Retain` reclaim policy on the StorageClasses exists to avoid.
- **A `toFQDNs` rule needs L7 DNS visibility to work** — Cilium learns a name's addresses by inspecting DNS answers, so the kube-dns egress rule in `platform/mysql/network-policy.yaml` carries `rules.dns.matchPattern: "*"`. Without it the FQDN entry never populates and every upload is dropped *while the name still resolves fine from inside the pod* — which is a genuinely confusing failure. Equally, that must remain the only DNS egress rule: a second, plain allow to kube-dns alongside it lets lookups bypass inspection and reintroduces the same bug.
- **The backup cron has six fields, not five** — `schedule: "0 30 2 * * *"` is 02:30:00 daily. CNMSQL's `ScheduledBackup` includes a seconds field, so a normal five-field crontab line is misparsed rather than rejected.
- **Both database network policies key off the operator's real pod labels** — `app.kubernetes.io/name: cloudnative-pg` in `cnpg-system`, `app.kubernetes.io/name: cnmsql` in `cnmsql`. Both were checked against the running pods; the CNMSQL operator also carries `control-plane: controller-manager`, which is not matched on.
- **CNPG's `Cluster` uses `imageName:`, which no built-in Renovate manager reads** — the `kubernetes` manager only looks at `image:`, and the repo's original custom manager only matches a bare `tag:`/`version:` value, not a full repository:tag reference. A second `customManagers` entry in `renovate.json` handles `imageName:` and splits the repo from the tag. Under `versioning=docker` the trailing `-1.1.1` is a compatibility suffix, so Renovate offers Postgres patch bumps *within* that VectorChord version and never moves the extension on its own — a VectorChord upgrade is a deliberate edit.
- **Every version in `flux/` is pinned exactly, so Renovate can see it** — the bot is Renovate (`renovate.json` at the repo root), not Dependabot; Dependabot has no Flux support at all. A floating `version: "*"` or `"1.21.x"` in a `HelmRelease` gives it nothing to bump, so upgrades happen silently at reconcile time with no PR and no record of what changed. Renovate's `flux` manager reads `HelmRelease.spec.chart.spec.version` and `OCIRepository.spec.ref.tag`; an image pinned *inside* a chart's `values:` is invisible to every built-in manager, so it needs a `# renovate: datasource=docker depName=<image>` comment on the line above `tag:` — the `customManagers` regex in `renovate.json` keys off exactly that.
- **Woodpecker steps are split across two sandboxes: kata for image builds, gVisor for everything else** — `woodpecker-sandbox` (two mutually exclusive rules, both reading the original `request.object` so one mutation cannot trigger the other). A step is routed to kata by *either* signal: pinning `runtimeClassName` in its own `backend_options` (`sysbox-runc`, `kata` and `kata-qemu` all mean "image build" and are normalised to `kata`), or carrying a `plugin-docker-buildx` container. The pin alone is not enough — a buildx step in a pipeline nobody has updated pins nothing, and sending that to gVisor unprivileged is a broken build with a confusing error. The image fallback is deliberately narrow (that one plugin, matched on the image *name*, since `*docker*` would also match the registry in `docker.io/library/golang`) and cannot be generalised: nothing in the manifest identifies a custom image running `kind` or dind, so those must pin `kata` themselves. Rule two is the exact negation of both conditions — keep the lists in step or a pod matches both rules. Everything else is rewritten to `gvisor` and has `privileged`/`allowPrivilegeEscalation` explicitly set to false, so a pipeline cannot grant itself privilege by writing it into its own backend_options. gVisor is not an option for the build steps: runsc does not implement enough of the mount and overlay surface for an inner container engine. The namespace carries `pod-security.kubernetes.io/enforce: privileged` because the kata half needs it, and `require-kata-for-privileged` is what stops that label from being a way onto the host.
- **The root cluster's sysbox approach does not port to kata, and the difference is `hostUsers`** — `woodpecker-sysbox-unprivileged` kept step containers unprivileged and set `hostUsers: false`, mapping container root to an unprivileged host uid. Kata has no user-namespace support to hang that on — the pod is a VM, there is no host uid to map to — and the kubelet rejects the combination. So privilege is granted instead of emulated and the isolation moves down a layer. Do not reintroduce `hostUsers: false` alongside a kata RuntimeClass.
- **`privileged: true` and `allowPrivilegeEscalation: false` is a kubelet-level rejection, not an admission one** — so `woodpecker-sandbox` raises `allowPrivilegeEscalation` alongside `privileged` in the kata rule. Woodpecker sets it to false on step containers; mutating only `privileged` produces a pod that is admitted and then fails to start, which looks like an image problem rather than a policy one.
- **A missing RuntimeClass is rejected before Kyverno ever runs, so no policy can mutate it away** — `RuntimeClass` is a built-in admission plugin that executes in the *mutation* phase (its job is copying `overhead` and `scheduling` onto the pod) and is ordered ahead of `MutatingAdmissionWebhook`, the one plugin under which every webhook runs. A pod naming a class that does not exist gets `pod rejected: RuntimeClass "x" not found` before Kyverno is consulted, even when a policy matching that exact pod would have rewritten the field. Confirmed by dry-running such a pod against the live cluster. The corollary: `kubectl apply --dry-run=server` runs the real admission chain, webhooks included, and is the cheapest way to settle any "who rejected this first" question.
- **`sysbox-runc` on ng is an alias for kata *and* the marker that sends a step there** — `infrastructure/kata/compat-sysbox-runc.yaml`. Pipelines carried over from the root cluster pin `backend_options.kubernetes.runtimeClassName: sysbox-runc`, which is both a name that has to resolve at admission and, to `woodpecker-sandbox`, the statement "this step runs a container engine". So it must keep pointing at kata: its `handler`, `overhead` and `scheduling` are read off this object *before* the rename, and pointing it at gVisor would schedule a pod by one class's rules onto another's runtime. **`RuntimeClass.handler` is immutable**, so changing which runtime the alias resolves to is a delete-and-recreate, not an edit — `kubectl delete runtimeclass sysbox-runc` and let Flux recreate it, or set `spec.force: true` on the `kata` Kustomization. Migration is pipelines swapping the name for `kata`; the field stays, since it is how a step asks for a VM. Delete the file once nothing names the old spelling.
- **Docker-in-kata needs `/var/lib/docker` on a tmpfs, and that is the one thing sysbox was doing for us** — inside a kata guest the container rootfs arrives over virtio-fs, which cannot serve as an overlay upper layer, so the inner dockerd fails on its first layer with `fstype: overlay … err: invalid argument`. Changing snapshotter or graphdriver does not help: the backing filesystem is the variable, not the code reaching it. sysbox provisioned `/var/lib/docker` on its own backing store to avoid exactly this; `woodpecker-docker-tmpfs` replaces it with an `emptyDir: {medium: Memory}`. That only works because overlayfs requires `trusted.*` xattrs on its upper filesystem and tmpfs gained them in **Linux 6.6** — the kata guest reports 6.18.35. On an older guest the mutation applies cleanly and the build fails identically, so check `uname -r` inside a kata pod before concluding the policy is broken.
- **The tmpfs is mounted on every step container, because targeting by image does not survive contact** — whatever needs it is "the step that runs a container engine", which is the buildx plugin in one pipeline and a custom image running `kind` in another, with no substring in common. `*docker*` to cover both also matches the *registry* in `docker.io/library/golang:1.24`, i.e. every image from Docker Hub. Mounting unconditionally is nearly free: a tmpfs allocates lazily, so an empty one costs a mount entry, and it shadows a /var/lib/docker that is empty in anything that is not already a docker image.
- **Kyverno's `+()` add-if-absent anchor does not hold inside a wildcard-matched container list** — under `- (name): "*"`, both `+(resources)` and the nested `+(limits)`/`+(requests)` form replaced a container's explicit `12Gi` with the policy's default rather than leaving it alone. Anything that must default a per-container field *only when unset* belongs in a `LimitRange` instead (`apps/woodpecker/limitrange.yaml`), where `default`/`defaultRequest` are applied by the LimitRanger plugin exclusively to containers that specified nothing — an API guarantee rather than a Kyverno behaviour to re-verify on each upgrade. A LimitRange is namespace-wide and cannot distinguish workloads, which is why woodpecker's server *and* agents carry explicit resources in `helm.yaml`; without them four idle agents would inherit CI's step defaults.
- **Kata sizes the guest from the pod's container limits** — with no limits it uses the runtime default (2 GiB), and woodpecker sets none on step containers. A build that OOMs inside the guest while the node has memory to spare is that default; the fix is resource limits on the step, not a bigger node.
- **The Infomaniak API token exists twice, once per namespace** — cert-manager's solver reads `infomaniak-api-credentials` in `cert-manager`, external-dns reads `infomaniak-credentials` in `external-dns`. Secrets do not cross namespaces; the token has to be created in both.
- **SOPS secrets *are* reconciled from git on `ng`** — the `sops-gpg` Secret exists in `flux-system`, and `platform/certificates`, `platform/external-dns` and `platform/mysql` each list their `*-sops.yaml` in `kustomization.yaml` and carry a `decryption: {provider: sops, secretRef: {name: sops-gpg}}` block in `ks.yaml`. Adding a secret means: write it with `stringData`, name it `*-sops.yaml` so `.sops.yaml` matches it, `sops -e -i` it, add it to the kustomization, and make sure that app's `ks.yaml` has the decryption block — a missing decryption block fails as the *encrypted* Secret being applied verbatim, not as an error. `sops-gpg` itself is the one secret applied out of band: it cannot come from the repo it unlocks.
- **Infomaniak has no floating IPs at all** — no network in the project is flagged `external`, so there is no pool to allocate from, and floating IPs are an IPv4 NAT construct with no IPv6 equivalent on any OpenStack. Instances attach directly to a shared dual-stack provider network (`ext-net1`: 21 public v4 /24s + `2001:1600:16:10::/64`, `dhcpv6-stateful`) and the port holds the public v4 and v6. `ext-v6only1` is the v6-only alternative. Do not reintroduce floating-IP or `enable_v6_fip`-style resources.
- **The edge-0 port is directly on the internet** — no NAT, no floating-IP indirection. The security group is the only thing in front of apid (50000) and the kubelet (10250). Neutron denies ingress by default, so the rules in `main.tf` are exhaustive; adding one exposes a port to the world.
- **edge-0's public IPv6 is ingress only** — never make it the node's Kubernetes address. `kubelet.nodeIP.validSubnets` pins the node to the WireGuard overlay; registering under the public v6 would route inter-node traffic over the open internet.
- **clouds.yaml entry names are `<project>-<region>`** (e.g. `PCP-SESBZOV-dc4-a`), not `openstack`. There is one entry per datacentre.
- **OpenStack provider v3 dropped the compute-side networking resources** — use `openstack_networking_port_v2` + `openstack_networking_floatingip_associate_v2`, not `openstack_compute_floatingip_associate_v2`.
- **The whole servarr stack runs on w-1 and that is a correctness requirement, not placement** — `apps/servarr` is one namespace around one RWO claim. `servarr-media` (3500Gi, `big-pool`) is mounted by jellyfin, sonarr, radarr, bazarr and qbittorrent at once, and RWO in Kubernetes is a *node* restriction rather than a pod one: Longhorn attaches the volume to one node and every pod scheduled there may mount it. So `nodeSelector: kubernetes.io/hostname: w-1` on each workload is what makes the stack work at all — a pod without it that lands elsewhere sits in ContainerCreating on Multi-Attach. RWX is not the alternative: Longhorn implements it with a share-manager pod re-exporting the volume over NFS, i.e. NFS on top of sparse files on top of ZFS to reach what used to be a directory. `/data` also has to stay *one* volume because qbittorrent seeds from `/data/downloads` while sonarr and radarr hardlink the same inodes into `/data/media`; hardlinks cannot cross a filesystem, so splitting downloads from media silently turns every import into a full copy.
- **Every stateful workload in `apps/servarr` is a StatefulSet at one replica, and the reason is at-most-one rather than ordinals** — each config claim is RWO and holds a sqlite database. A StatefulSet deletes the old pod and waits for it to actually be gone before creating its replacement; a Deployment can only say that via `strategy: Recreate`, which is one edit away from a rolling update that either deadlocks on Multi-Attach or, worse, *succeeds* because both pods landed on w-1 and lets two processes open one database. `flaresolverr` is the only Deployment there — no volume, nothing to be at-most-one about — and correspondingly the only workload with no `nodeSelector`.
- **The config claims are on `big-pool` even though `longhorn` would be more durable** — a config volume on the sata pool would be genuinely 3-replicated, but every pod that opens one also mounts `servarr-media`, which pins it to w-1, so each sqlite write would cross the LAN while a `big-pool` replica is local to the node the engine runs on. Latency beats a replica count the workload cannot move to take advantage of. The consequence is the class's, not this app's: w-1 going down takes the whole stack, and `talos.sh upgrade w-1` hits `block-if-contains-last-replica` once per claim.
- **A storage Kustomization must not carry `wait: true` on this cluster** — every StorageClass is `volumeBindingMode: WaitForFirstConsumer`, so a freshly applied PVC sits `Pending` until something mounts it, and kstatus reports a Pending PVC as InProgress. `wait: true` therefore blocks until a consumer appears, while the consumer is gated behind that same Kustomization by `dependsOn` — a deadlock with no timeout short of the KS's own. `apps/servarr/storage` omits it deliberately and says so; `dependsOn` without `wait` still guarantees the claims were applied, which is the only ordering the migrate Jobs need. `apps/immich/storage` and `apps/home-assistant/storage` still have `wait: true` and got away with it because their claims were bound by hand before Flux first reconciled them.
- **ExtAuth on ng is a `SecurityPolicy` per route, because Envoy Gateway has no `GatewayExtension`** — the root cluster's shape (one kgateway `GatewayExtension` naming the authentik outpost + one `TrafficPolicy` per route) collapses into a single `SecurityPolicy` per route, so the `ak-outpost-proxy.authentik:9000` coordinates and the `/outpost.goauthentik.io/auth/envoy` path are repeated per app in `apps/servarr/routes.yaml`. That is the API, not a missing abstraction. Two things must be stated explicitly: `headersToExtAuth` has to include `cookie`, because Envoy sends only Host/Method/Path/Content-Length/Authorization to an HTTP auth service by default and the cookie is the header the whole flow turns on; and the cross-namespace consent is a `ReferenceGrant` in `apps/authentik/reference-grant.yaml`, whose absence fails *open* — `ResolvedRefs=False`, the filter is dropped, and the route keeps serving unauthenticated.
- **Envoy Gateway 1.8.3 cannot express `headersToClientOnSuccess`, and only half of that matters** — kgateway's `authorizationResponse.headersToClient` is unnecessary because Envoy already does it: with `allowed_client_headers` unset, a *denied* auth response reaches the client with all its headers, so the 302 to `auth.yewolf.fr` keeps `location` and `set-cookie`. The gap is `allowed_client_headers_on_success`, which EG never sets and offers no field for, so a `set-cookie` authentik emits alongside a 200 (session refresh or rotation) never reaches the browser. Login works; a session that would have been silently extended instead expires and asks again.
- **The `authentik` CiliumNetworkPolicy does not cover the outposts, and its port-9000 rule implies it does** — `app.kubernetes.io/instance: authentik` is a chart label, and the outpost pods are reconciled by authentik's own Kubernetes outpost controller from provider definitions in the database, carrying `app.kubernetes.io/name: authentik-outpost-proxy`/`-ldap` and no instance label. So `ak-outpost-proxy` — the ext-auth backend for every SSO-protected route — is selected by no policy and is default-allow, and 9000 is the outpost's port rather than the server's. Closing it means a second policy selecting the proxy outpost by `name`; the LDAP outpost beside it has consumers outside this repo, so a policy written blind for either fails closed on a working path.
- **"On the tailnet *and* behind SSO" is a different wiring from "public and behind SSO", and the outpost plays the opposite role in each** — the public apps (`servarr`, `ytdlp`) keep an `HTTPRoute` on the Envoy Gateway and call `ak-outpost-proxy` as an *ext-auth service* via a `SecurityPolicy`; their authentik providers are `mode: forward_domain`. That form needs a Gateway listener, which is exactly what a tailnet-only app must not have. `apps/cloudbeaver` inverts it: the tailscale `Ingress` points at an outpost itself and the outpost *is* the reverse proxy (`mode: proxy`, external host `https://cloudbeaver.goby-beaufort.ts.net`, internal host the KEDA interceptor — see the scale-to-zero bullet below). That outpost is a *second* one, `ak-outpost-proxy-tailnet`, holding only this provider: a single outpost can only ever emit one session-cookie domain, so a ts.net provider and the yewolf.fr ones cannot share a process. The full mechanism is in `apps/authentik/cloudbeaver-ingress.yaml`; the symptom, if it is ever undone, is a 400 on the OAuth callback. Two consequences worth stating: the Ingress lives in `apps/authentik/cloudbeaver-ingress.yaml` because an Ingress backend must be a Service in its own namespace, and the app's policy deliberately does *not* admit the `tailscale` namespace the way every other tailnet app does — that rule would be a second door straight past the SSO gate, and everything would still look like it was working. The provider itself is not in git; like every other authentik object here it lives in the database.
- **Scale-to-zero without an HTTPRoute, which is the first of its kind here** — the other three scaled apps put the interceptor behind a Gateway listener; `apps/cloudbeaver` has no listener to put it behind, so the *authentik provider's internal host* is what points at `keda-add-ons-http-interceptor-proxy.keda:8080`. That works because the outpost forwards the Host header untouched: `proxyModifyRequest` in authentik's `mode_proxy.go` rewrites `r.URL.Host` and sets `X-Forwarded-Host`, but leaves `r.Host` alone unless a per-user `HostHeader` claim exists, and Go's `ReverseProxy` sends `req.Host` when set. So the InterceptorRoute matches on `cloudbeaver.goby-beaufort.ts.net` — the browser's own Host, three hops upstream. Two consequences: `platform/keda/network-policy.yaml` has to admit the outpost on 8080 (it previously admitted only Envoy, and the comment there already predicted this case), and there is **no** entry in `platform/keda/reference-grants.yaml`, because those grants exist for a cross-namespace HTTPRoute `backendRef` and there is no HTTPRoute.
- **CloudBeaver's ingress rule got wider when it started scaling to zero, and the argument that it is still safe is external to the policy** — it now admits the KEDA interceptor rather than the outpost pod, and that interceptor is shared with three publicly routed apps. It is not a bypass: the interceptor selects its backend by Host, reaching CloudBeaver requires `cloudbeaver.goby-beaufort.ts.net`, and no HTTPRoute in the cluster carries that hostname — so such a request to the public Gateway is a 404 at Envoy and never reaches the interceptor. **Giving CloudBeaver a public HTTPRoute would silently collapse that argument.** Also note `cooldownPeriod: 1800` rather than cyberchef's 300: scaling this to zero drops open SQL editor sessions and pooled JDBC connections, and coming back costs a JVM start plus a Longhorn detach/attach on the RWO workspace volume.
- **CloudBeaver is anonymous-access on purpose, and that is only safe because of the two settings beside it** — `CLOUDBEAVER_APP_ANONYMOUS_ACCESS_ENABLED` plus `..._GRANT_CONNECTIONS_ACCESS_TO_ANONYMOUS_TEAM` mean whoever authentik lets through lands straight in a session holding root on both shared databases, with no second password to share around. What keeps that bounded is `CLOUDBEAVER_APP_SUPPORTS_CUSTOM_CONNECTIONS: "false"` (the two seeded connections are the entire reachable surface — an anonymous user cannot point it at anything else) and the network policy's egress being an enumeration of `postgres:5432` and `mysql:3306` with no `world`. `CB_ADMIN_NAME`/`CB_ADMIN_PASSWORD` are still set from `admin-sops.yaml`: not as a gate, but because without them the server boots into its first-run setup wizard and offers it to whoever arrives first. Turning any of these three off changes what the SSO gate is actually protecting — make the argument each time.
- **The seeded connections are a first-boot artefact, not desired state** — `run-cloudbeaver-server.sh` copies `conf/initial-data-sources.conf` to `workspace/GlobalConfiguration/.dbeaver/data-sources.json` *only* when `workspace/.metadata` does not exist, and CloudBeaver rewrites the credentials into its own encrypted store the first time each connection is used. So the init container in `apps/cloudbeaver` renders that file on every start and it is ignored on every start but the first. Rotating a database password therefore does not reach an already-seeded CloudBeaver: fix the connection in the UI, or delete the PVC and let it re-seed. The renderer escapes `"` and `\` for the same reason — both operators generate alphanumeric passwords today, and it is the *rotation* to something with a quote in it that would silently produce an unparseable file, a server in configuration mode, and nothing obvious in the log.
- **`enableSuperuserAccess` on `platform/postgres` exists for exactly one consumer** — CNPG defaults it to false, which does not merely leave the password unset: it runs `ALTER ROLE postgres WITH PASSWORD NULL` and deletes the secret. It is on so `platform/postgres/applications/cloudbeaver` has a `postgres-superuser` to push. No app may reference that secret — every app gets its own role and database via a `Database` CR. Both CloudBeaver directories under `applications/` are the only ones that declare no `Database`: it exists to reach the databases the others create.
- **`mysql-root` is unusable off the socket, and the password is not what is wrong** — CNMSQL creates exactly one root row and its host is `localhost`, so `mysql.user` has no `root@'%'` and a client anywhere on the network gets `Access denied for user 'root'@'<pod-dns-name>' (using password: YES)` while holding the correct secret. MySQL matched a different, nonexistent account; nothing about the credential is at fault, which is why the error sends you looking in the wrong place. This is the one asymmetry with the Postgres side, where enabling `enableSuperuserAccess` is genuinely enough. The fix is declarative rather than a hand-made `root@'%'` that git would not know about and a restore would not recreate: `platform/mysql/applications/cloudbeaver/databaseuser.yaml` is a `cloudbeaver` account at `host: "%"` with **`superuser: true`** — `ALL PRIVILEGES ON *.* WITH GRANT OPTION`, root exactly. The password is ours rather than the operator's, hence the SOPS file in that directory and none in the Postgres one.
- **`superuser: true` on a `DatabaseUser` is not interchangeable with `grants: [{on: "*.*", privileges: [ALL]}]`, and the failure is delayed and mute** — the two fields are mutually exclusive, and the admission webhook accepts the grants form and then refuses it at reconcile: *"ALL on \*.\* is not allowed: it grants every dynamic admin privilege ... or set superuser=true"*. Nothing rejects the apply, Flux reports the Kustomization healthy, and the DatabaseUser sits with `APPLIED` blank and `Ready=False` while the MySQL account is never created. At the client that reads as `Access denied for user '<name>'@'<pod-dns-name>' (using password: YES)` — indistinguishable from a wrong password, which sends you to the secret instead of to `kubectl -n mysql get databaseuser`. `WITH GRANT OPTION` is separately inexpressible in a grants entry: MySQL takes it only as a trailing clause, so `privileges: [ALL, GRANT OPTION]` emits `GRANT ALL, GRANT OPTION ON *.*`, a plain syntax error the CRD schema is happy to admit.
- **`apps/servarr` has one namespace-wide network policy rather than eight, and one rule in it is the security control** — the eight workloads are peers with identical needs (resolve names, talk to each other constantly, reach an indexer or metadata API), so per-workload files would be eight copies of the same rules with the real distinctions buried in the duplication. Internet egress is `toCIDRSet: 0.0.0.0/0` excepting `10.0.0.0/8` and `192.168.0.0/16`, **not** `toEntities: world` — those are not the same thing, because `world` means "outside the cluster" and includes the home LAN and the router, which is exactly what a stack parsing attacker-supplied data from indexers and torrent peers must not reach. All ports are open outbound on purpose: private trackers listen on arbitrary ports and gluetun dials whatever port NordVPN's server list returns, so narrowing it breaks indexers one at a time, months later.
- **The `servarr` namespace is `privileged` PSA for gluetun, not for hostPath** — the migrate Jobs' hostPath mounts are one-shots that will eventually be deletable; `NET_ADMIN` is not in baseline's capability allow-list, so the namespace stays above baseline for as long as the torrent stack routes through a tunnel. Nothing there sets `securityContext.privileged`, so `require-kata-for-privileged` never fires and no Kyverno exclusion is needed. The three torrent containers share one pod deliberately: qbittorrent and rustatio must be in gluetun's network namespace or the kill switch is not a kill switch — split into separate pods, qbittorrent falls back to the pod's own default route the moment the tunnel drops.
- **Jellyfin on ng has no hardware transcoding, and it is the same physical machine that had a GPU** — home1's pod ran `runtimeClassName: nvidia` with `nvidia.com/gpu: 1`, but w-1's Talos image carries zfs/kata/gvisor/sysbox and no NVIDIA extensions, so there is no device plugin and no `/dev/dri`. Getting it back is `siderolabs/nonfree-kmod-nvidia-production` + `siderolabs/nvidia-container-toolkit-production` in w-1's `extensions:`, a `talos.sh upgrade w-1`, an `nvidia` RuntimeClass and the device plugin DaemonSet — deliberate work, not a field on the workload.
- **Nine tailnet hostnames, and nothing gathers them any more** — `dashboard`, `esphome`, `zigbee2mqtt`, `qbittorrent`, `joal`, `scrutiny`, `radar`, `longhorn`, `cloudbeaver`. `cloudbeaver` is the odd one: its Ingress is in the `authentik` namespace, not the app's, and it is the only one of the nine that is not reachable from the tailnet alone (see the SSO bullet above). It is also what replaces the root cluster's `pgadmin` and `phpmyadmin` devices. On the root cluster the Caddy in `apps/dashboard` reverse-proxied five of these onto one device under sub-paths; ported to ng it serves a static index that *links* to each instead, so its `Caddyfile` has no `reverse_proxy` and its network policy is `egress: []` — not decoration, an empty list turns egress enforcement on and then permits nothing, which is right for a pod that resolves no names and dials no backends. Sub-path proxying is what forced the change: it needs an app that either emits relative asset paths or can be told its base path (scrutiny's `SCRUTINY_WEB_LISTEN_BASEPATH`, which ng's deployment deliberately does not set), and rustatio/joal and radar are root-anchored SPAs that can never be sub-pathed at all. Restoring a proxy block means restoring the egress and DNS rules with it, or it fails at name resolution with nothing in the Caddy log to say so. `esphome` and `zigbee2mqtt` exist as devices only because of this — they had no Ingress at all while the dashboard proxied them.
- **qbittorrent's migrated config has `WebUI\HostHeaderValidation=true`** and the Tailscale proxy passes the original Host through, so it serves "Unauthorized" until the ts hostname is added to Options → WebUI → "Server domains" — a runtime setting in the app's own database with no env var and nothing a manifest can do about it. Caddy rewrote the Host on the root cluster, which is why the question never came up there; it comes up again on every rename, including the `-ng` strip.
- **State management** — both `router/` and `openstack/` use `tf.sh` wrappers with PGP-encrypted state files (`terraform-state.gpg`). They share the same PGP key.

## Rules

- **NEVER** read terraform state files (`*.tfstate`, `*.tfstate.backup`, `.terraform/`).
- **NEVER** read SOPS-encrypted files or decrypted secrets. Use `data.sops_file` in Terraform — do not inspect actual credential values.
- **NEVER** commit secrets, private keys, or unencrypted credentials.
- When adding a new WireGuard peer, run `./wireguard/gen-identity.sh <name> <address>` from the repo root, then update `router/main.tf` locals if needed.
- **Before planning `openstack/`**, run `talos/talos.sh schematic` and `talos/talos.sh render edge-0` — the module reads `talos/out/schematic-id` and `talos/out/edge-0.yaml` and has preconditions that say so. The full bring-up order (floating IP first, because the router needs it as the peer endpoint) is in `talos/README.md` under "The cloud worker".

## State management

State is encrypted with SOPS and committed to git. Use the wrapper script (`tf.sh`) instead of calling terraform directly — it decrypts state before use and re-encrypts on exit.

State file: `router/terraform-state.gpg` (PGP-encrypted blob, tracked in git)
Plaintext: `router/terraform.tfstate` (temporary, gitignored, never committed)
